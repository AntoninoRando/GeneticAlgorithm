The code

Architecture map

Two languages, one process. Python loads data and drives the loop. A header-only C++17 library does all the heavy work and is compiled into a Python module called scheduler.

Why two languages?

Fitness evaluation dominates the run time: each generation decodes every tree on every world, and each decode evaluates the tree thousands of times. For \(N\) decisions, \(n\) candidates and rule size \(R\), Sun et al. put the cost of one generation at \(O(N \cdot n \cdot R)\) (mtgp_multicloud §4.4). C++ with -O3 and OpenMP makes that fast. Python keeps data handling, configuration and plotting simple. PERFORMANCE.md records the speed-ups and how they were measured.

Read the top comment of every header first

Each header starts with a LITERATURE NOTES block that explains which paper each design choice comes from and where the project deviates. It is the fastest way to understand why the code looks the way it does.

The bridge: bindings.cpp

Uses pybind11 to expose the C++ classes to Python with their default arguments. The names stay the same, except evaluateMany, evaluateSingle and constantTerminals, which become evaluate_many, evaluate_single and constant_terminals in Python. evaluate_single returns a tuple (completion_ratio, mean_response, energy).

When you add a parameter to a C++ method, add it in bindings.cpp too, with a py::arg and a default that keeps the old behaviour.

What is deliberately not in git

  • The compiled module (scheduler*.so) and build/: built per machine, stale after any C++ change.
  • The data (data/): see Day one, step 2. The synthetic demo data in data/demo/ is regenerated on every --demo run, so it is not committed either.
  • Run outputs (metrics/, snapshots/).
  • Generated documentation (docs/build, except the linked PDF) and the papers in thesis/papers/.

The rules are in .gitignore. .gitattributes fixes the line endings of shell scripts (see Day one, step 1).

One call, end to end

What happens when main.py runs one generation:

  1. fitness_evaluator.evaluate(population, snapshot) crosses into C++.
  2. In FitnessEvaluator::evaluatePointers, an OpenMP loop gives each thread some individuals. For each one, detail::greedyDecode builds a schedule and sumObjectives measures it.
  3. Back on one thread, response time and energy are min-max normalised across the population (or, with fixedBounds, divided by bounds computed once per world), and fitness is written into each GPIndividual. The objects are shared with Python, not copied.
  4. Python reads the best fitness, decides whether to switch worlds, records metrics.
  5. genetic_algorithm.solveNextGeneration() crosses into C++ again: sort, elitism, then a second OpenMP loop breeds offspring pairs. Each pair has its own random-number stream, so a seeded run gives the same result on any number of threads.

Conventions you must keep

  • Higher score is better, both for a tree's output and for fitness. Some papers use the opposite convention, so watch the sign when you compare formulas.
  • Defaults reproduce the old behaviour. Every literature option is off by default, so the same seed gives the same evolution as before. New options should follow the same rule.
  • Do not rename public C++ functions without updating bindings.cpp and the Python callers (AGENT.md).
  • Randomness goes through the given mt19937, never rand() or a new random_device, or seeded runs stop being reproducible.
  • Python references into the population go stale. getPopulation() returns a live view of the C++ vector. After solveNextGeneration() that vector is replaced, so an individual you saved from before the call points to freed memory. Call getPopulation() again after each generation, as main.py does.
