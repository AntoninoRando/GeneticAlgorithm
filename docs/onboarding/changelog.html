2026-11-20: realistic data without the original log

  • Code change: new package data_processing/realistic_trace (orbits.py, scenario.py, simulator.py, generate.py): a re-implementation of the simulator of Magliarisi et al. on real Starlink orbits (CelesTrak elements, SGP4) that writes a task log with the original 27 columns to data/realistic/ and splits it into worlds. New --worlds-dir flag and worlds_dir key in main.py, the same flag in the two experiment scripts, runConfigurations/realistic.json, sgp4 in requirements.txt, a --baselines-only flag in run_experiments.py, and tests/test_realistic_trace.py (46 tests). Without the new flag nothing changes. No change to the GP, the decoder, the fitness or the loader.
  • Realistic data (new page, in "The code"): the three kinds of data, how to generate and use the realistic one, the model step by step with its equations, the one fitted parameter and how it is fitted, a comparison with the published figures and with the baselines recorded on the original worlds, the source of every parameter, where the program differs from the thesis text, the limits, and how to cite generated data.
  • Data pipeline: new section "No original log? Realistic data"; "ask your supervisor" now names the alternatives.
  • Day one: the generator in the "No worlds?" box and the examples, --worlds-dir in the flag table, the new test file, and --worlds-dir for the experiment scripts.
  • Known quirks: two new entries: the time unit of the data is very likely seconds, not minutes; the real orbits never reach the formula. The config.json5 row now says its values are copied by hand into the generator.
  • Architecture, Where to start, Welcome: the new package and test file; what is not in git; a recipe "I cannot get the original data"; a pointer.
  • Glossary: nine terms (buffer zone, calibration, deadline, discrete-event simulation, elevation angle, listening dome, orbital elements, realistic data, SGP4).
  • References: added the simulator's public source code (cosmos2025, checked through the GitHub API) and the SGP4 reference (vallado2006spacetrack, already in the bibliography, metadata checked again on Crossref, not read). Thesis Chapter 6 of magliarisi2026thesis was read for the model. Notes in thesis/literature_notes.md §11.
  • Later the same day: a refused download now shows CelesTrak's own answer (which names the time of the last download), and a transfer that breaks off is saved as starlink_incomplete.csv instead of being lost or passed off as complete. New section "If the download fails" on the Realistic data page. The "No data found" message of main.py now says whether generated worlds exist and which flag selects them (Day one, Realistic data).
  • First experiment on generated data (same day): run_experiments.py --baselines-only now also prints the energy ceiling on \(C\) for any rule (new function completion_ceiling). New section "What to expect when you train on it" on the Realistic data page: why only about a quarter of the jobs can be scheduled, with the bound, and a 10-seed comparison of four existing configurations on the generated worlds (results in thesis/experiments/results_ablation_realistic/). Known quirks and Experiments point to it. No algorithm change; the options compared and their references were already in the guide.
  • Not done: the generator has not been compared with the original log (not available) and has only been run on an incomplete orbit file (about half the constellation). The first experiment uses one data seed and has not been repeated on a complete orbit file or on the original worlds.

2026-11-20: the scheduler in 3D

  • Guide change only. No change to the C++ core, the Python runners or the algorithm, so no new references.
  • The scheduler in 3D (new page, in "Concepts"): the Earth, 15 satellites on three orbits, the links between them and a Create task button. A task flies to the access point, every satellite shows the score the chosen formula gives it, the best feasible one wins, and the task hops to it over the links. Rejected tasks fall back red. The page has the rule selector of the playground, both tie-breaks, a batch mode, two battery settings ("roomy" and "like our data"), a live table of what the decoder sees, and a table "What is real and what is simplified".
  • New files: assets/viz3d.js (a JavaScript mirror of the selection and commit blocks of detail::greedyDecode, plus the three.js scene) and assets/formula.js (the formula parser, moved out of the decoder page so both pages share it). Viz3D.selfTest() in the browser console replays the worked examples of the decoder page. three.js r128 is loaded from cdnjs.
  • Decoder & fitness: the playground now uses the shared parser (same behaviour); two pointers to the 3D view.
  • Welcome, The problem, Giving a demo: pointers to the new page; the demo script shows it at minute 3.
  • Glossary: two terms (hop, inter-satellite link).
  • Architecture, Where to start: the three script files of the guide; a new recipe "change the 3D view"; the decoder recipe now lists the two JavaScript copies of the selection rule.
  • Not modelled, and said so on the page: orbits, links, routes and flight times are drawings. The program has no such simulation.

2026-11-14: depth-aware crossover and mutation (opt-in)

  • Code change: two options of SchedulerGP.initialize(), depthAwareCrossover and depthAwareMutation (tree_operators.h, scheduler_gp.h, bindings.cpp), the flags --depth-aware-crossover and --depth-aware-mutation in main.py, four configurations in thesis/experiments/run_ablation.py, and a DepthAwareOperators test class. With them the operators never build a tree above the depth cap, instead of building one and returning a copy of the parent. The default operators are unchanged.
  • One generation: new subsections under crossover and mutation: what goes wrong at the cap, the fitting test, and the fix; two rows in the options table.
  • Theory & maths §6: new subsection with the probabilities of a parent copy (0.32 for two full trees at cap 4; 62% and 42% of subtree replacements at depths 3 and 2), the proof that a fitting second point always exists, and what the unit tests measure; two new rows in the design map.
  • Known quirks: new entry "At the depth cap, crossover and mutation often do nothing".
  • Experiments: a "not measured yet" box with the command.
  • Day one, Glossary: the flags; two terms (depth-aware operators, height of a node).
  • References: added the Field Guide to GP (Poli, Langdon, McPhee 2008), whose §11.3.2 was read, and Langdon 2000 (metadata verified, not read). Also in thesis/references.bib and thesis/literature_notes.md §10.
  • Not done: no experiment on the held-out worlds.

2026-11-14: build flags follow the build type

  • Code change: CMakeLists.txt used to add -O3 to every build, so Debug was not a debug build, and its flags were GCC-only. Now RelWithDebInfo (optimised, with symbols) is the default and the build for experiments, Debug is really unoptimised, and the GCC flags are skipped on other compilers. Every script, the dev container, the VS Code tasks and CI pass the build type explicitly. The module reports scheduler.build_type and scheduler.optimized, and importing an unoptimised module raises a RuntimeWarning. No algorithm change; the optimised build uses the same flags as before.
  • Day one: step 3 explains build types with a table, how to check which build is loaded, and a warning about experiments on a Debug build and about build/ remembering its type; the script table and the debugging section are updated.
  • Known quirks: the CMake entry now only says that an MSVC build is untested.

2026-11-14: typed flags always override the configuration file

  • Code change: main.py used to detect a command-line override by comparing the value with its default, so a typed flag equal to the default (-c default --generations 200) lost to the file. The parser now records only the flags that were typed, and the layering lives in resolve_config(). On/off options gained a --no-… form and there is a new --enable-metrics. New tests/test_config.py. No algorithm change.
  • Day one: step 5 states the rule with the example; the flag table lists --enable-metrics and the --no-… forms; the tests section mentions the new test file.
  • Architecture: resolve_config and the new test file.
  • Known quirks: removed the entry for this bug.
