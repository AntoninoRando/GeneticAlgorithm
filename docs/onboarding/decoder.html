Decoder & fitness

A tree is only a formula. The greedy decoder turns it into a schedule, and the fitness function turns the schedule into one number. Both live in fitness_evaluator.h.

1. The greedy decoder

detail::greedyDecode(tree, registry, snapshot, …) repeats one simple step: among all pairs (unscheduled job, satellite) that are still feasible, commit the one with the highest score.

every satellite s:  free_at[s] ← τ          # snapshot time
jobs with arrival > τ are skipped
score[j][s] ← tree(j, s) for all j, s       # computed once
loop:
    best ← argmax over unscheduled j, all s, of score[j][s]
           among pairs where  free_at[s] + d_j ≤ sunset[s]      # sunset
                         and  rate[s] · d_j  ≤ energy[s]        # battery
    if no feasible pair: stop                # remaining jobs are rejected
    commit best (j*, s*):
        start = free_at[s*], completion = start + d_j*
        free_at[s*] = completion
        energy[s*] -= rate[s*] · d_j*
        completedTasks[s*] += 1
    recompute score[·][s*] for unscheduled jobs   # only s* changed

Details that matter:

  • Ties are broken by scan order: jobs in file order, then satellites in order, and a pair only wins if its score is strictly higher. A formula that ignores the satellite (for example job.arrivalTime) therefore always picks the first feasible satellite, which amounts to "first-fit".
  • Infeasible pairs are skipped before the score is read. A formula cannot "choose" to break a constraint (magliarisi2026thesis §6.3.1, icdcs_sc §III-C).
  • The decoder chooses the job and the satellite with the same formula. The papers usually evolve separate rules for "which task next" and "which machine" (zhang2025mtgper §2.2, mtgp_multicloud §4.1). The project starts with one tree deliberately; see theory.
  • Batch, not dynamic: every job is visible at once, and the decoder picks the globally best pair each round. The papers instead react to one event at a time.

Satelliteenergy \(E_s\)sunset \(\omega_s\)

Use shortest job first, the tree NEG(ADD(job.executionTime, job.transferTime)), so the score is \(-d_j\):

  1. Best score is J1 (−6). Both satellites tie, so S0 wins by scan order. S0: free at 16, energy 14.
  2. Next is J3 (−10). On S0: \(16+10 = 26 \le 40\) and \(10 \le 14\). Feasible, so S0. S0: free at 26, energy 4.
  3. Next is J0 (−12). On S0 the energy check fails (\(12 > 4\)). On S1: \(10+12 = 22 \le 35\) and \(12 \le 30\). So S1. S1: free at 22, energy 18.
  4. J4 (−18): S0 lacks energy; on S1, \(22 + 18 = 40 > 35\) breaks the sunset. J2 (−24): breaks the sunset on both. No feasible pair: stop.

Result: 3 of 5 jobs scheduled, so \(C = 0.6\). Response times are J1 \(16-3=13\), J3 \(26-9=17\) and J0 \(22-0=22\), so \(R = 17.33\). Energy \(\mathcal{E} = 6+10+12 = 28\).

4. The score cache and its cost

A naive decoder would re-evaluate the tree for every pair on every round: up to \(J\) rounds × \(J S\) pairs, so \(O(J^2 S)\) tree evaluations. The trick: a score depends only on the job, which never changes, and the satellite, which changes only when a job is committed to it. So:

  • compute the \(J \times S\) matrix once: \(JS\) evaluations;
  • after each commit, refresh only that satellite's column: at most \(J\) evaluations per round, \(J^2\) in total.
$$\text{tree evaluations: } O(J^2 S) \;\longrightarrow\; O(JS + J^2)$$

The argmax scan is still \(O(JS)\) comparisons per round, but those are cheap next to a tree walk. Selection is byte-for-byte the same as without the cache, which PERFORMANCE.md verified. Working buffers are thread_local, so they are allocated once per thread instead of once per decode.

5. From schedule to fitness

After decoding every individual \(i\) we have raw objectives \((C_i, R_i, \mathcal{E}_i)\). They are combined in FitnessEvaluator::evaluatePointers:

$$ f_i \;=\; w_C\, C_i \;-\; w_R\, \hat R_i \;-\; w_E\, \hat{\mathcal E}_i, \qquad (w_C, w_R, w_E) = (0.60,\ 0.25,\ 0.15)$$

where the hats are min-max normalisation across the current population:

$$\hat x_i = \frac{x_i - \min_k x_k}{\max_k x_k - \min_k x_k} \in [0,1], \qquad \hat x_i = 0 \text{ if all } x_k \text{ are equal.}$$
  • \(C_i\) is not normalised. It is already in [0, 1], and keeping it absolute preserves selection pressure when the whole population ties on cost.
  • For \(R\), individuals that scheduled nothing are left out of the min and max and get \(\hat R_i = 1\), the worst value. Otherwise an empty schedule would report \(R = 0\), the best possible.
  • \(\mathcal{E}\) uses plain min-max: zero energy for zero jobs is a true value.

Worked example: why the weights are delicate

Three individuals in one population:

\(C\)\(R\)\(\mathcal{E}\)\(\hat R\)\(\hat{\mathcal E}\)fitness
A: schedules many0.7517.328110.60·0.75 − 0.25 − 0.15 = 0.050
B: schedules few, fast0.5012.01600.5710.30 − 0 − 0.086 = 0.214
C: schedules nothing0n/a0100 − 0.25 − 0 = −0.250

B beats A although A completes 50% more jobs. Because \(\hat R\) and \(\hat{\mathcal E}\) are relative, the individual with the worst cost always pays the full 0.40 penalty. The completion bonus of A over B is only \(0.6 \times 0.25 = 0.15\). This is the "misalignment" the thesis observed: long runs drift toward rules that schedule few, short jobs (results). The theory page discusses alternatives (lexicographic, Pareto).

Fitness is only comparable inside one population and one world

The same tree gets a different fitness in a different population or a different world. To compare trees across runs, re-score them with evaluate_single, which returns the raw \((C, R, \mathcal{E})\). The experiments do exactly that.

The fixed-bound alternative (--fixed-bounds)

The example shows two problems. The mean response time \(R\) ignores the jobs that were not scheduled, and min-max stretches every cost to the full [0, 1] range, whatever its real spread. The opt-in fixed-bound fitness (FitnessEvaluator.fixedBounds = True, or --fixed-bounds in main.py) changes two things:

  • Divide by bounds of the world, not of the population. For each world the evaluator computes \(R^{\max}\), the longest response time any schedule could produce, and \(\mathcal{E}^{\max}\), the most energy any schedule could spend. Both depend on the snapshot only.
  • Charge unscheduled jobs. A job that is not scheduled counts as if it had the worst response, \(R^{\max}\). This is a rejection penalty.
$$\tilde R_i = \frac{1}{N}\Big[\sum_{\text{scheduled } j} \frac{c_j - a_j}{R^{\max}} + (\text{number unscheduled})\Big] = 1 - C_i\Big(1 - \frac{R_i}{R^{\max}}\Big), \qquad \tilde{\mathcal E}_i = \frac{\mathcal E_i}{\mathcal E^{\max}}$$ $$ f_i^{\text{fix}} \;=\; w_C\, C_i \;-\; w_R\, \tilde R_i \;-\; w_E\, \tilde{\mathcal E}_i $$

The same three individuals, in a world with \(R^{\max} = 30\) minutes and \(\mathcal{E}^{\max} = 40\):

\(C\)\(R\)\(\mathcal{E}\)\(\tilde R\)\(\tilde{\mathcal E}\)fitness
A: schedules many0.7517.3281 − 0.75·(1 − 17.3/30) = 0.6830.700.450 − 0.171 − 0.105 = 0.174
B: schedules few, fast0.5012.0161 − 0.50·(1 − 12/30) = 0.7000.400.300 − 0.175 − 0.060 = 0.065
C: schedules nothing0n/a0100 − 0.25 − 0 = −0.250

Now A beats B. B's jobs are faster, but half of its jobs are missing and each missing job costs a full unit, so its response term (0.700) is worse than A's (0.683). The numbers also stay the same if a fourth individual joins the population, which is not true of the table above.

How \(R^{\max}\) and \(\mathcal{E}^{\max}\) are computed, why they are valid bounds, and the sources are on the theory page. The code is detail::computeWorldBounds in fitness_evaluator.h; from Python, FitnessEvaluator.world_bounds(snapshot) returns the pair.

Off by default, and not yet measured

All thesis results use the population-relative fitness. The fixed-bound fitness has proven properties (see theory) and unit tests, but nobody has yet run it on the held-out worlds. Do not write that it "works better" until the ablation has been run (results).

6. Several worlds at once

evaluate_many(population, snapshots) decodes each individual on every world and pools the raw sums before normalising:

$$C_i = \frac{\sum_w |\mathcal A_{i,w}|}{\sum_w N_w}, \qquad R_i = \frac{\sum_w \sum_{\mathcal A_{i,w}} (c_j - a_j)}{\sum_w |\mathcal A_{i,w}|}, \qquad \mathcal E_i = \sum_w \mathcal E_{i,w}$$

Pooling, rather than averaging per-world ratios, gives every job the same weight and keeps "no job scheduled" well defined. Empty worlds are skipped. With one world, evaluate_many gives exactly the same result as evaluate, and a unit test checks this.

With the fixed-bound fitness the pooling is per job too: each response is divided by the \(R^{\max}_w\) of its own world before the sum, and the energy term is \(\sum_w \mathcal E_{i,w} / \sum_w \mathcal E^{\max}_w\).
