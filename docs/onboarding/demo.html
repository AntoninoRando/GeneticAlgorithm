1. Demo mode: running without the data

The real input, data/example.csv, is not in git (data pipeline). Without it main.py has nothing to train on. Demo mode fixes that for demonstrations:

./run demo --no-start-prompt          # same as: python3 main.py -c demo --no-start-prompt

It does three things:

  1. data_processing/demo_data.py writes a synthetic task log, data/demo/trace.csv, with the same columns as the real one: about 600 tasks over 60 minutes on 12 made-up satellites (DEMO-SAT-01 … 12).
  2. The real splitter cuts it into 6 ten-minute worlds in data/demo/worlds/.
  3. main.py trains on those worlds instead of data/worlds/. Everything from here on is the normal code path: data factory, C++ decoder, fitness, breeding.

The configuration runConfigurations/demo.json asks for a small, seeded run (population 60, depth 4, 60 generations, seed 1), which takes under a second on a laptop. It writes the metrics plot to metrics/demo_metrics.png. Any flag still works on top of it, for example ./run demo --generations 300.

How the synthetic log is generated
  • Each satellite gets a fixed speed, link quality, starting energy, energy drain and typical queue length, drawn once.
  • Arrivals form a Poisson process of 10 tasks per minute, which means the gaps between arrivals are exponentially distributed and independent. A 10-minute world then holds about 100 tasks, like a real one.
  • Each task gets a type, an amount of work and an image size. Execution time = work ÷ speed of the server, transfer time = image size ÷ link quality. The server is drawn at random, so the log does not contain a good schedule to copy.
  • The seed of the data is fixed (DEMO_SEED = 2026), so every machine gets the same demo worlds. --seed only changes the evolution.
Demo numbers mean nothing

The generator is a toy. It is not fitted to the real log and does not model orbits. Its only job is to give every column some variation, and one real pattern (faster servers finish sooner) for the GP to find. Never report, plot or compare results from demo mode, and never choose a parameter with it. The program prints a DEMO MODE banner at the start and a reminder at the end, and the files live in data/demo/, apart from data/worlds/. Show the thesis numbers on the results page instead.

2. Prepare (10 minutes, the day before)

  1. Get a Linux environment. On Windows or macOS, open the repository in VS Code and choose Reopen in Container (Docker must be running). The first start builds the module, see day one.
  2. Check it works. In the container terminal: 
    python3 -c "import scheduler; print(scheduler.build_type, scheduler.optimized)"   # RelWithDebInfo True
python3 -m unittest discover -s tests
./run demo --no-start-prompt
    The tests should end in OK; without the real data, 13 of them are skipped, which is expected.
  3. Open the guide offline-safe. Open docs/onboarding/index.html in a browser (double-click it; no server needed). The formulas are drawn by KaTeX from a CDN: with no internet they appear as raw LaTeX, so check the room's network, or open each page once beforehand.
  4. Have the thesis ready. thesis/main.pdf has the formal version of everything.
  5. If you do have the real data, put it in data/example.csv and run the splitter (day one, step 2). Then you can also show a real run, without demo.

Tips
  • Show the reproducibility: run ./run demo --no-start-prompt twice and point out that the last line is identical. Then add --seed 2 and it changes.
  • To show a world switch more often, add --convergence-threshold 5.
  • To show snapshot inspection, add --inspect-snapshots: it prints the jobs and satellites of each world.
  • If metrics/demo_metrics.png is not created, numpy or matplotlib is missing (outside the container): add --disable-metrics and skip that step.

4. Questions you will get

Why not use an exact solver or a hand-made rule?
Even its simplest special case is NP-hard (the problem, "Why not solve it exactly?"), and a satellite must decide in microseconds (theory §1). A hand-made rule is one guess; GP searches the space of rules. The hand-made rules are in the results table as baselines.
Is the demo data real?
No. It is synthetic, to show the pipeline without the simulator's log. The real numbers are on the results page and in the thesis.
Why is only about a quarter of the jobs completed?
Battery energy is the binding constraint: each satellite can afford only one or two jobs (data pipeline, "Energy is the binding constraint"). The demo data is set up the same way on purpose.
How do you know a change is an improvement?
Several seeds, a train/test split of worlds and a Mann–Whitney test; never a single run (theory §8).
