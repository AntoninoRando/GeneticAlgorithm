Concepts

Genetic programming from zero

Genetic programming (GP) evolves small programs the way breeders improve plants: keep the best, cross them, add some random variation, repeat. This page explains every piece using the formulas this project actually evolves.

From genetic algorithms to genetic programming

A genetic algorithm (GA) searches for a good solution by keeping a population of candidates. Each candidate (an individual) gets a fitness, a number saying how good it is. Better individuals are more likely to become parents. Parents produce offspring through crossover (combining two parents) and mutation (random small changes). One round of this is a generation.

In a classic GA an individual is a fixed-length string, such as a list of numbers. In genetic programming an individual is a program, usually stored as a tree. GP was introduced by John Koza (koza1992book, koza1994gp). Our programs are arithmetic formulas, so "program" and "formula" mean the same thing here.

Our individuals: priority formulas

Each individual is one formula that takes a (job, satellite) pair and returns a number, its priority score. Higher means "schedule this job on this satellite first". For example:

$$\text{score}(j, s) \;=\; a_j \;-\; \frac{e_j}{\max(\text{completed}_s,\ \text{bandwidth}_s)}$$

Evaluating a tree, by hand

Evaluation is recursive: evaluate the children, then apply the operator. Take a job with \(a_j = 7\), \(e_j = 20\) on a satellite with 1 completed task and bandwidth 10.6:

  1. MAX(1, 10.6) = 10.6
  2. 20 /? 10.6 = 1.887
  3. 7 − 1.887 = 5.113, the priority of this pair.

In C++ this is ExprNode::eval() in expr_tree.h: a switch on the node type that calls itself on the children.

Why "protected" division? Closure.

Crossover can put any subtree under any operator, so every operator must accept every value it might receive. Koza calls this closure (koza1994gp §4). A plain division would crash or return infinity when the denominator is 0. The papers we follow return 1 in that case (mtgp_multicloud §4.2, zhang2025mtgper §3.2.2). This project returns 0, a documented deviation kept so that older results stay valid. The six binary operators are exactly the function set of those two papers. NEG, ABS and INV are this project's additions.

The terminal set: 18 inputs

Terminals are listed in buildTerminalRegistry() in registry.h. Each one is a name plus a small function that reads a field from the job or the satellite:

  • 7 job terminals: job.arrivalTime, job.ram, job.disk, job.imageSize, job.executionTime, job.transferTime, job.numberOfHops.
  • 11 satellite terminals: sat.elevationAngle, sat.latency, sat.bandwidth, sat.completedTasks, sat.cpuBusyUntil, sat.networkBusyUntil, sat.cpuCapacity, sat.networkCapacity, sat.energyReserved, sat.remainingEnergy, sat.loadRatio.

There are no numeric constants (no "ephemeral random constants" such as 0.37): every leaf is a terminal, as in the papers we follow (mtgp_multicloud Table 2, zhang2025mtgper Table 2).

Four terminals are always zero

In our data sat.cpuBusyUntil, sat.networkBusyUntil, sat.energyReserved and sat.loadRatio are 0 for every satellite. A leaf with one of them contributes nothing. --prune-constant-terminals stops GP from drawing them, and --track-busy-until turns sat.cpuBusyUntil into a live "free at" value.

Why a formula and not a schedule?

We could evolve a schedule directly (a list "job 3 → satellite 7, …"). That would only solve one snapshot. A formula is a rule: given any new snapshot, the greedy decoder applies it to build a schedule. An algorithm that searches the space of heuristics, instead of the space of solutions, is called a hyper-heuristic (burke2013hyperheuristics). GP is the most common way to build one for scheduling (branke2016automated, nguyen2017gpsurvey). This setup is called GPHH (GP hyper-heuristic).

The evolutionary loop

population ← 100 random trees                     # ramped half-and-half
repeat for G generations:
    for each tree:  schedule ← decode(tree, world)  # C++, parallel
                    fitness  ← score(schedule)
    next ← copy of the 2 best trees                 # elitism
    while next is not full:
        p1, p2 ← two tournament winners             # selection
        c1, c2 ← crossover(p1, p2)  with prob 0.8
        mutate(c1); mutate(c2)                      # per-node prob 0.08
        maybe hoist(c1), hoist(c2)                  # prob 0.05 each
        add c1, c2 to next
    population ← next
    if no improvement for 10 generations: switch world

Each step in plain words:

1. Initialisation

Random trees are built with ramped half-and-half (koza1994gp §4). Half of them use the full method, where every branch reaches the same depth. The other half use grow, where branches may stop early. The target depth is "ramped" across a range, for example 2 to 7. The goal is a first population with many different shapes and sizes.

2. Evaluation

Every tree is run through the decoder on the current world, and the resulting schedule is scored. This is the expensive part, done in C++ with OpenMP. Details: Decoder & fitness.

3. Selection: tournaments

To pick a parent, draw 5 individuals at random and keep the fittest. This is tournament selection. Bigger tournaments favour the best individuals more strongly (more selection pressure). The theory page works out the exact probabilities.

4. Elitism

The 2 best individuals are copied unchanged into the next generation, so the best fitness found so far is never lost.

6. Mutation: small random edits

Each node of a child has an 8% chance of being mutated:

  • a terminal is replaced by another random terminal (job.ram → sat.latency);
  • an operator is swapped for a different one with the same arity (ADD → MIN), keeping its children;
  • or, in 10% of operator mutations, the whole subtree is thrown away and regrown at random (subtree mutation).

7. Hoist: fight bloat

GP trees tend to grow larger over generations without getting better. This is called bloat (luke2006bloat). With probability 5%, an offspring is replaced by one of its own subtrees (hoist mutation), which makes it smaller. A hard depth cap (default 7, 4 in most experiments) also bounds every tree.

What you should take away

  • An individual is a tree-shaped formula that scores (job, satellite) pairs.
  • The formula only becomes a schedule through the decoder, and the schedule determines the fitness.
  • Evolution is selection (tournaments + elitism) plus variation (crossover, mutation, hoist).
  • Every one of these choices comes from a paper, except a few project additions that are labelled as such. The generation page maps each line of code to its source.
