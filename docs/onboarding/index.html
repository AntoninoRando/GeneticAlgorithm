Onboarding guide

Welcome to the GP Scheduler

This guide is for your first days on the project. It assumes you can program in Python and read C++, and nothing else: no genetic programming, no satellites, no knowledge of this codebase.

The project in one minute

Satellites in low Earth orbit can carry small computers. People on the ground send them computing jobs (for example "process this image"). Someone has to decide which satellite runs which job, and in what order. That decision is called scheduling.

A schedule is good when it completes many jobs, completes them fast and uses little energy. There are also hard rules: a satellite flies out of reach at some point (its sunset), and its battery is limited.

We do not write the scheduling rule by hand. We let the computer evolve it with genetic programming (GP):

  1. A rule is a small formula, such as -(job.executionTime + job.transferTime). It gives a score to every (job, satellite) pair, and a higher score means "do this pair first".
  2. We start with 100 random formulas.
  3. We test each formula by running it inside a simple scheduler (the decoder) on realistic data, and we measure how good the resulting schedule is (its fitness).
  4. The better formulas get to "reproduce": we mix pieces of them (crossover) and change small parts at random (mutation).
  5. We repeat for hundreds of generations. The formulas get better over time.

The output is a scheduling heuristic, a formula a satellite could evaluate in microseconds, not a one-off schedule. That is what makes this approach a hyper-heuristic: an algorithm that designs algorithms.

Who built what

  • The problem and data come from research on satellite edge computing by Magliarisi, Casalicchio and colleagues. Their simulator produced the task log we train on (magliarisi2025orbit).
  • The method follows the genetic-programming hyper-heuristic literature: Koza for GP itself, and recent papers that evolve scheduling rules for cloud, fog and satellite computing (references).
  • The code is a C++17 library compiled into a Python module called scheduler, plus Python scripts that load data, run the evolution and record metrics.
  • The thesis in thesis/ describes the method and the experiments formally. This guide is the friendly version and links to it.

Two rules of this project

1. Every algorithm choice must be backed by the literature and the maths

If you change how the GP works (an operator, a parameter, the fitness), you must point to a peer-reviewed paper that supports the choice, write down its mathematical definition, and test it with several seeds and a statistical test. If no paper supports it, say so and label it as a project-specific choice. Look for the LITERATURE NOTES comments at the top of each header in include/scheduler/: they show what this looks like.

2. Keep this guide up to date

If your change makes a page here wrong, fix the page in the same change and add a line to the changelog. Both rules are written in CLAUDE.md at the repository root.
