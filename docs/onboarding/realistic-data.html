The code

Realistic data without the original log

The original task log is not in the repository and you may not be able to get it. data_processing/realistic_trace writes a log with the same 27 columns by re-running the published simulation model on real Starlink orbits. This page says how to use it, what it models, where every number comes from, and what it is not.

The realistic log follows the same model and the same settings file, and it is checked against the published figures (below). It is still a different program run on different orbits. Say "generated with a re-implementation of the simulator" wherever you report a number obtained on it, and never put results on data/realistic/ and on data/worlds/ in the same table.

How to use it

pip install sgp4                                         # once; it is in requirements.txt
python3 -m data_processing.realistic_trace --download    # first time: fetch the orbits (about 1.7 MB) and generate
python3 -m data_processing.realistic_trace               # later: reuse data/orbits/starlink.csv
./run realistic --no-start-prompt                        # train on data/realistic/worlds

The second command prints a table that compares the generated data with the published figures. Read it every time: it is the only evidence that the data resembles the original.

The files in data/realistic/:

  • trace.csv: the log. Same columns, in the same order, as the simulator's result file, so it can stand in for data/example.csv.
  • worlds/: the log cut into 10-second windows by the usual splitter.
  • visibility.csv: for every topology update and satellite, its elevation, the time left before it sets, and whether it is an access point. Nothing reads it yet (limits).
  • report.json: the settings, the orbit file's name, SHA-256 and epoch, the statistics of every run and the comparison with the thesis. Keep it with any result you report.

Any worlds directory works with python3 main.py --worlds-dir DIR. The experiment scripts take the same flag: python3 thesis/experiments/run_ablation.py --worlds-dir data/realistic/worlds trains on worlds 0 to 19 and tests on all the others.

Keep the orbit file

CelesTrak refreshes its data every two hours and refuses a second download inside that period. More importantly, a new file gives a new trace. Download once, keep data/orbits/starlink.csv, and quote its SHA-256 from report.json.

How it works

1. Real orbits

CelesTrak publishes the orbital elements of every Starlink satellite: six numbers that fix the size, shape and orientation of an orbit and where the satellite was on it at a reference time, the epoch. The classic text format is the TLE (two-line element set). The generator reads TLE and OMM CSV, the newer format: TLE has room for five-digit catalogue numbers only, and Starlink has passed 100000.

SGP4 is the standard model that turns these elements into a position at any time (vallado2006spacetrack). It is not optional: the elements are fitted with SGP4, so they give the right position only with SGP4. The original simulator uses the same chain (magliarisi2025orbit §3.2).

SGP4 answers in a frame that does not rotate with the Earth. orbits.py rotates it by the Earth's rotation angle \(\theta\) (Greenwich mean sidereal time) to get a position fixed to the ground:

$$x' = x\cos\theta + y\sin\theta,\qquad y' = -x\sin\theta + y\cos\theta,\qquad z' = z.$$

With \(\boldsymbol\rho\) the vector from the ground user to the satellite and \(\hat{\mathbf u}\) the vertical at the user, the elevation angle, the height of the satellite above the horizon, is

$$\varphi = \arcsin\frac{\boldsymbol\rho\cdot\hat{\mathbf u}}{\lVert\boldsymbol\rho\rVert}.$$

The ground user is in Rome (41.8967° N, 12.4822° E), as in config.json5.

2. The network at one instant

  • Listening dome. Satellites with \(\varphi \ge 40^\circ\). Only they execute requests. Every satellite here is a SEN, a satellite edge node: a satellite with a computer on board.
  • Buffer zone. Satellites with \(25^\circ < \varphi < 40^\circ\): about to enter or just left. They only pass results along.
  • Neighbours. Two satellites less than 659 km apart have an inter-satellite link (ISL), a laser link.
  • Access points (APs). The 5 dome satellites nearest to the user among those still approaching it. Requests enter the network through them.
  • Sunset. For a dome satellite, the seconds left before it drops below 40°. In the paper a pass through the dome lasts 25 to 176 s, 138.5 s on average (magliarisi2025orbit §3.4).

3. The requests

Requests arrive as a Poisson process of rate \(\lambda = 10\) per second. Each request \(r\) has:

TypeShareCPU demand \(c_r\) (mean)Payload \(s_r\)After the CPU
Generic_Service0.400.05 s10–88 KBresult sent down to the user
CPU_Intensive0.350.5 s10–88 KBresult sent down to the user
CPU_and_Data_Intensive0.250.5 s22 KB–2.2 MB (30%), 2.2–24.2 MB (50%), 132.5–500 MB (20%)a network stage on the satellite

CPU demands are exponentially distributed. Two derived quantities, with \(b^{isl} = 2150\) MB/s the link rate (thesis Eqs. 6.1 and 6.2):

$$c^{net}_r = \frac{s_r}{b^{isl}},\qquad D_r = (1+\delta_D)\,(c_r + c^{net}_r),\quad \delta_D = 0.1.$$

\(D_r\) is the deadline, counted from the arrival. It leaves only 10% of slack: a request that has to wait for long is lost.

Worked example

A CPU-intensive request with \(c_r = 0.5\) s and \(s_r = 0.05\) MB has \(c^{net}_r = 0.05/2150 \approx 2\times10^{-5}\) s and \(D_r = 1.1 \times 0.50002 \approx 0.55\) s. It can wait 0.05 s at most.

4. What the simulated system does

The log records the decisions of the system's own scheduler, the one the thesis wants to improve on. For a request arriving at time \(t\):

  1. Entry. It enters at the AP with the highest score $$\sigma_j(r) = w_e\,\frac{B_j}{B_{\max}} - w_R\,\frac{W_j}{D_r},\qquad w_e = 0.7,\ w_R = 0.3,$$ where \(B_j\) is the node's battery, \(B_{\max}\) the fullest battery among the APs, and \(W_j\) the node's estimated waiting time. The score is \(-\infty\) if the node cannot meet the deadline or lacks the energy.
  2. Choice. The AP looks at its neighbours that are in the dome, best score first. It keeps those whose estimated completion time \(\hat T_j\) is below the deadline and, for OrbitAware, below the node's sunset: \(\hat T_j < D_r\) and \(\hat T_j < T^{res}_j\). The first one gets the request. DTS drops the sunset test. If no node is left, the request is rejected.
  3. Execution. The node checks energy and deadline again, then runs the request: a CPU stage with 5 slots, first come first served, then the network stage or the downlink.
  4. Way back. The result goes to an AP by greedy routing, one hop every 0.5 s: to a neighbouring AP if there is one, else to the unvisited neighbour nearest to the user.

The waiting time of a stage with \(m\) slots is estimated from the work in front of the request. With \(r_{\min}\) the shortest remaining time among the running requests if all slots are busy (0 otherwise) and \(A\) the total remaining work, running and queued:

$$W = r_{\min} + \frac{\max(0,\ A - m\,r_{\min})}{m}.$$

5. Energy

Every satellite starts with a battery of 100 kJ that never recharges. Running a request costs (thesis Eq. 6.3, a dynamic-voltage-scaling model):

$$\varepsilon^{cpu}_r = e\,c_r\,C^3,\qquad \varepsilon^{net}_r = P_{net}\,c^{net}_r,\qquad e = 5\times10^{-26},\ P_{net} = 1\ \text{W},$$

with \(C\) the CPU frequency in hertz. A node accepts a request only if its battery, minus what is already promised to accepted requests, covers the cost.

Worked example

At \(C = 4.6\) GHz the 0.5 s request above costs \(5\times10^{-26} \times 0.5 \times (4.6\times10^{9})^3 \approx 2430\) J. A full battery pays for 41 of them: a node that serves two such requests per second is empty after 20 seconds. This is why most rejections in the thesis are for energy.

The one fitted parameter

The original simulator charges CPU energy with a single frequency \(C\) for all satellites, drawn at random once per run between 10 MHz and 10 GHz. The thesis does not report the value. Because energy grows with \(C^3\), this number alone decides the outcome: with the orbit file used for this page, no request is refused for energy below about 4 GHz, and two thirds of all requests are refused at 6 GHz.

By default the generator calibrates it. It picks the \(C\) for which the simulated system is closest to the two figures the thesis gives for this setting: a success rate of 75.7% and 61% of the rejections due to energy (magliarisi2026thesis §6.5.1). With \(S(C)\) and \(G(C)\) these two quantities averaged over the first three runs:

$$C^\star = \arg\min_{C \in [1,\,10]\ \text{GHz}} \big(S(C) - 0.757\big)^2 + \big(G(C) - 0.61\big)^2,$$

searched on 16 logarithmically spaced values and then on 7 more around the best one. One parameter cannot match two numbers exactly. The gap that remains is printed after every generation and is the honest measure of how close the re-implementation is.

--energy-cpu-hz draw draws \(C\) per run as the original does (runs then range from "no energy problem" to "nothing gets done"), and --energy-cpu-hz 4.5e9 fixes it.

The thesis reports that load concentrates on the top 3–4 nodes; here the top 4 take 19% of the work, so the generated load is probably more evenly spread than the original.

Where the program and the thesis text differ

The log you are replacing was written by the program, so the generator follows the program. Each difference from the text of Chapter 6:

TopicThesis textProgram, and this generator
CPU demanduniform on 0.01–0.1 s and 0.1–1 sexponential with mean 0.05 s and 0.5 s, no bounds
Frequency in the energy chargeeach node's own \(C_i\)one \(C\) for the run; \(C_i\) only in the scheduler's estimate
Choice of nodesmallest estimated response time (Eq. 6.7)highest score \(\sigma_j\) among the nodes that pass the tests
Waiting estimatequeued demands plus half the request's ownthe work-based formula above
The AP itselfa candidate like its neighboursnever chosen: every request moves exactly one hop
Completion estimatetransfer counted oncethe payload's time on the link counted twice
Relocation when no node fitsrandom or "max sunset"none: the request is rejected
Memory and storagecheckeddrawn but never checked

The text's waiting estimate cannot be the one that ran: it adds \(0.5\,c_r\) to every request, which alone exceeds the 10% of slack the deadline allows, so no request would ever be accepted.

Three deliberate departures from the program, all small: a result's transmission energy is computed in consistent units (the program mixes MB and bytes, which makes it a million times too small; either way it is under a joule per request); a result moves exactly one hop per routing tick; and the background batch requests load the network but get no row in the log (--log-batch writes them).

Limits you must know

  • It is a re-implementation. It was written from the thesis, the settings file and the behaviour of the public code. It reproduces two published numbers approximately, and the baselines behave on it as on the original worlds. It has never been compared with the original log itself, because that log was not available.
  • The orbits are today's. Starlink has many more satellites now than when the thesis was written, so the network is denser. The thesis does not state the date of its orbit data.
  • The loader throws most of the realism away. Steps 2 and 3 of the pipeline rescale every column per world and draw each satellite's sunset at random. The real sunsets and elevations are in visibility.csv, unused. Feeding them to create_satellites_from_csv would be the most valuable next step, and it is a change to the problem instance: discuss it before doing it.
  • The clock is in seconds. The thesis and config.json5 give the simulated time as 300 seconds, and this generator works in seconds. The rest of the project calls the same numbers minutes. The pipeline only compares them with each other, so results do not change, but the label is very likely wrong (known quirks).
  • Rows include rejected requests. Like the simulator's file, the log has a row for every request the system logged, completed or rejected (about 28% here). The loader turns each row into a job. Rejected rows have no transfer time, hop count or queue length (N/A), which the loader replaces by mid-range values.
  • Not modelled: the ILP baselines, B.A.T.M.A.N. routing and its control messages, priority classes (Chapter 5 of the thesis), and failures of links.
The original simulator is public

Its source is at github.com/DMagliarisi/COSMOS (cosmos2025). Running it is the way to get a log from the original program. It has no licence file, so ask its author, who works with your supervisor, before you use or redistribute it. This generator copies no code from it.

Using generated data in the thesis

  • Name the data: "traces generated with a re-implementation of the simulator of [thesis], on Starlink orbital elements of [date] from CelesTrak, seed 2026". Give the orbit file's SHA-256 and the fitted \(C\).
  • The splitter orders worlds by time, so worlds 0–19 are the first 200 seconds of run 0 and the test set is everything after. With 5 runs that means 20 training worlds and 130 test worlds, 120 of them from four runs the GP never saw: a stricter test than the original 20/10 split. Training on worlds from several runs needs a change to N_TRAIN in run_experiments.py.
  • Repeat every experiment with several GP seeds and test with the Mann–Whitney U test, as on the experiments page. A generator also lets you vary the data seed: do it, and report both.
  • No result obtained on generated data exists yet. Nothing in the thesis may be replaced by one silently.
