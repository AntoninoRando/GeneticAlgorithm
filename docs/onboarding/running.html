1. Get an environment

The project is developed on Linux inside a VS Code dev container. The scheduler module is a compiled extension (a .so file) that only loads in the Python version and on the CPU it was built for. For that reason it is not stored in git: every machine builds its own copy (step 3), and the container does it for you on first start.

  1. Install Docker and VS Code with the Dev Containers extension.
  2. Open the repository folder and choose Reopen in Container.
  3. The first start runs .devcontainer/postCreate.sh. It installs numpy, matplotlib, pybind11 and the debug tools, then builds the module.

Without the container you need Python 3, CMake ≥ 3.15, a C++17 compiler, pybind11, numpy and matplotlib (see requirements.txt). OpenMP is optional: without it everything still works, just on one core.

On Windows: line endings

Windows text files end lines with two characters (CR LF), Linux with one (LF). A shell script with Windows endings fails inside the container with bash\r: No such file or directory. The file .gitattributes tells git to keep *.sh and run in LF on every platform, so a Windows checkout works in the container. If you still see that error, your copy is older than that file: run git add --renormalize . && git checkout -- run scripts .devcontainer.

2. Get the data

The data/ folder is not in git (it is listed in .gitignore). Ask your supervisor for data/example.csv, the task log of one 300-minute simulation (2960 rows). Then split it into 30 "worlds" of 10 minutes each:

python3 -m data_processing.csv_preprocessing.world_splitter \
    --csv data/example.csv --output-dir data/worlds --window-minutes 10

You now have data/worlds/world_000.csv … world_029.csv and a manifest.json. The data pipeline page explains what the splitter does and why.

No worlds?

main.py falls back to data/example.csv if data/worlds/ is empty, and prints a reminder to run the splitter. If data/example.csv is missing too, it stops with a message that tells you where to put the file. The unit tests that need data/worlds are skipped.

3. Build the scheduler module

From the repository root:

cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo -DPYTHON_EXECUTABLE=$(which python3)
cmake --build build --target scheduler

The helper scripts/build.sh runs exactly these two commands, from any directory. What happens:

  • CMakeLists.txt compiles bindings.cpp (which includes every header in include/scheduler/) into a pybind11 module called scheduler.
  • The .so file is written directly into the repository root (LIBRARY_OUTPUT_DIRECTORY), so import scheduler works from there. You do not need to copy it.
  • The build type (CMAKE_BUILD_TYPE) decides how the compiler optimises. RelWithDebInfo means "release with debug information": fully optimised (-O3) but still carrying the symbols a debugger needs. It is the default, and the one to use for every experiment. An unoptimised module was once the main reason runs were slow (see PERFORMANCE.md).
  • If CMake finds OpenMP it prints "OpenMP found: fitness evaluation will run in parallel."

Check it worked, and which build you got:

python3 -c "import scheduler; print(scheduler.build_type, scheduler.optimized)"   # RelWithDebInfo True
Build typeWhat you getUse it for
RelWithDebInfo (default)-O3 -funroll-loops -g, assertions offexperiments and everyday work
Release, MinSizeRelthe same optimisation; pybind11 also strips the symbols and enables link-time optimisationa module to hand to someone else
Debug-O0 -g: no optimisation, assertions ona debugger, nothing else
Never run experiments on a Debug build

A Debug module gives results, just many times later, and its timings mean nothing. Three things protect you. CMake prints a warning when it configures Debug. import scheduler raises a RuntimeWarning when the module is unoptimised. And scheduler.optimized is False. One trap remains: the build/ folder remembers the build type of its last configuration. After a debug session, a bare cmake --build build builds Debug again. Always pass -DCMAKE_BUILD_TYPE=…, or use the scripts below, which do.

Rebuild after every C++ change

Python runs the .so, not the headers. If you edit bindings.cpp or anything in include/scheduler/ and forget to rebuild, Python silently keeps running the old code. A new option then fails with AttributeError or TypeError; a changed formula just gives the old numbers. The .so is ignored by git (*.so in .gitignore), so it never arrives with a git pull either.

The helper scripts in scripts/ all work from any directory:

4. Run an evolution

A short, reproducible run that finishes in seconds:

python3 main.py --no-start-prompt --generations 50 --population 50 \
    --max-depth 4 --seed 1 --print-every 10

What you will see:

  • PID: …: printed so you can attach a debugger (see below).
  • Loaded 30 pre-processed world(s).
  • New best fitness in world: … each time the best individual improves.
  • Convergence detected after 10 generations… when the best fitness stops improving for 10 generations: the program then switches to the next world.
  • Every 10 generations, a SCHEDULE SNAPSHOT with the best tree and the population's structural diversity (share of distinct trees).
  • At the end: Jobs scheduled: …% | Mean response: … min | Energy: … Wmin for the best tree on the last world.

Without --no-start-prompt the program waits for Enter before starting. Without --seed every run is different.

5. Configure a run

Settings come from three layers. Each one overrides the previous:

  1. built-in defaults in default_config() in main.py;
  2. a JSON file in runConfigurations/ (for example default.json, robust.json), selected with -c NAME;
  3. the command-line flags you typed. A typed flag always wins, even if its value equals the built-in default: -c default --generations 200 runs 200 generations, not the file's 5000.
python3 main.py -c robust --no-start-prompt          # 5000 gens, depth 4, clone retries + 3 worlds
./run default --generations 10                       # ./run NAME is short for: python3 main.py -c NAME

The flags you will use most

FlagDefaultMeaning
--population100Number of formulas per generation.
--generations200Number of generations.
--max-depth7Maximum tree depth. The run configurations and the thesis use 4.
--hoist-rate0.05Chance that an offspring is replaced by one of its own subtrees (anti-bloat).
--convergence-threshold10Generations without improvement before switching to the next world.
--csv-row-limit100Jobs loaded per world (≤ 0 = all).
--seed-1≥ 0 makes the run fully reproducible, whatever the thread count.
--clone-retries0Re-mutate offspring that are copies of a parent or an elite. 3 helps (see results).
--worlds-per-eval1Score every formula on K worlds at once. 3 helps.
--tournament-size5Selection pressure.
--fixed-boundsoffFixed-bound fitness: costs divided by per-world bounds, unscheduled jobs penalised. Makes fitness comparable across generations. Not yet measured (see decoder & fitness).
--disable-metrics, --enable-metricsSkip or force the CSV/NPZ/PNG metrics. Both shipped configuration files turn metrics off; --enable-metrics turns them back on.
--no-<option>Every on/off option has a negative form (--no-fixed-bounds, --no-terminal-weighting, …) to switch off something a configuration file switched on.

Other literature options (--initial-max-depth, --internal-crossover-bias, --terminal-weighting, --track-busy-until, --prune-constant-terminals) are explained on the generation page. Run python3 main.py --help for the full list.

Two things you cannot set from the command line

The crossover rate (0.80) and the per-node mutation rate (0.08) are the defaults of SchedulerGP.initialize() in bindings.cpp. main.py does not pass them. The fitness weights (0.60 / 0.25 / 0.15) are attributes of FitnessEvaluator and are also not exposed. To change them, edit main.py.

What is config.json5?

It is the configuration of the upstream satellite simulator that produced the data (orbit altitude, sunset elevation, energy budget, …). No code in this repository reads it. It is kept as a record of how the data was generated.

6. Read the outputs

  • Metrics (on by default) go to metrics/: <prefix>_metrics.csv (one row per generation), .npz (the same as NumPy arrays) and .png (plots). Written by metrics_tracker.py. Columns: best and mean fitness, fitness standard deviation, the best individual's completion ratio, mean response and energy, the snapshot size, the stagnation counter, and whether the world was reset.
  • Snapshots (--inspect-snapshots, --save-snapshots) print or save the world the population was scored on, at the start, at each reset and at the end. Draw one with python3 snapshot_timeline_plot.py snapshots/<file>.json.
Do not compare fitness across worlds

Fitness is normalised within the current population (see Decoder & fitness). A best fitness of 0.40 in world 3 and 0.35 in world 4 does not mean the formula got worse. Compare the raw metrics instead (completion ratio, mean response, energy). With --fixed-bounds fitness is comparable between generations of the same world, but still not between worlds, because each world has its own bounds.

7. Run the tests

python3 -m unittest discover -s tests -v

tests/test_paper_features.py checks the literature features against independent computations: the terminal-weight solver against the worked example in Yang's thesis, multi-world pooling, the busy-until terminal, seeded reproducibility, depth caps, excluded terminals, clone retries, tournament pressure and the fixed-bound fitness. Run it after every C++ change, together with a short seeded run.

tests/test_config.py checks the three configuration layers of step 5 (defaults, file, typed flags) through main.resolve_config().

Tests that read data/worlds are reported as skipped when the data is missing; the others build small worlds in code. Continuous integration (CI, a service that runs checks automatically) does the same on GitHub: .github/workflows/ci.yml builds the module and runs this command on every push and pull request. It has no data, so it runs only the tests that need none.

8. Re-run the thesis experiments

python3 thesis/experiments/run_experiments.py --out thesis/experiments/results
python3 thesis/experiments/make_report.py
python3 thesis/experiments/run_ablation.py --seeds 20

These take a long time (many seeds × many configurations). Ask before starting them on a shared machine. The results page explains the setup.

9. Debug the C++ from Python

The C++ runs inside the Python process, so you debug it by attaching gdb to Python:

  • VS Code: use the (debug) Launch main.py configuration, or start python3 main.py and use (debug) Attach to main.py with the printed PID. The prompt "Press Enter to start" gives you time to attach.
  • Terminal: scripts/debug_cpp.sh --generations 5 builds with symbols and starts main.py under gdb. By hand: gdb -p <PID>, or gdb python3 then set breakpoint pending on and run main.py.

Which build to debug with:

  • The normal RelWithDebInfo module has symbols, so breakpoints and backtraces work, but the optimiser removes some variables and reorders lines. It is enough to find where something happens, at full speed.
  • To inspect every variable and step line by line, build Debug: scripts/build-debug.sh, or scripts/debug_cpp.sh, which also starts gdb. Use a small run (--generations 5 --population 20), because it is slow. Rebuild with scripts/build.sh when you are done.
