Where do I start if…

Recipes for the changes people make most often. Each one lists the files to touch, in order, and what to check afterwards.

Before any change to the algorithm

Read the LITERATURE NOTES at the top of the header you are changing and the relevant entry in thesis/literature_notes.md. Find a paper that supports the change, write down the maths, and plan a seeded experiment with a statistical test. If no paper supports it, say so in the code and the thesis. These are project rules (CLAUDE.md).

…I want to add a new input feature (terminal)

  1. If the value is not already a field, add it to Job or Satellite in types.h and to the struct binding in bindings.cpp.
  2. Fill it in data_processing/data_factory.py.
  3. Append an entry to buildTerminalRegistry() in registry.h. Appending keeps the indices of existing terminals, which saved trees and tests rely on.
  4. If the decoder updates it during a decode (like completedTasks), update it at commit time in greedyDecode, and exempt it in FitnessEvaluator::constantTerminals.
  5. Add a row to the terminal table in registry.h's notes and on the GP basics page.

…I want to add an operator

  1. Add it to NodeType and ARITY in expr_tree.h, and handle it in eval() and toString(). Keep closure: define it for every input.
  2. Add it to kBinaryOps or kUnaryOps in tree_builder.h.
  3. Check that every simplification rule is still exact.
  4. Expose it in the NodeType enum binding, and update tostr in thesis/experiments/run_experiments.py.

…I want to change the fitness function

  1. FitnessEvaluator::evaluatePointers in fitness_evaluator.h: steps 2 (normalisation) and 3 (weights). There are two modes. The default is population-relative. With fixedBounds the function returns early from the block marked "Fixed-bound fitness", and the bounds come from detail::computeWorldBounds.
  2. If you change a decoder constraint (sunset, energy, start times), re-check computeWorldBounds: its proof (Proposition 1 in thesis/chapters/method.tex) relies on jobs running back to back from the snapshot minute and on the two feasibility filters.
  3. Keep evaluate and evaluate_many consistent (one world must equal evaluate; there is a test for it).
  4. Read theory §5 first. This is the most consequential change you can make.
  5. Re-run the main experiment and the weight study; update results.

…I want to change how the decoder picks a pair

  1. The selection is the innermost block of detail::greedyDecode in fitness_evaluator.h. It has two branches: the default (strictly higher score, ties by index) and earliestFreeTieBreak.
  2. Keep the default branch byte-for-byte: every thesis number and every seeded run depends on it. Add a new behaviour as a new opt-in branch.
  3. Read theory §3, ties. Proposition 2 in thesis/chapters/method.tex assumes the key (score, −start, −job, −satellite).
  4. A decoder change affects baselines as much as evolved rules. Re-score both (results).
  5. The guide has two JavaScript copies of the selection rule: the playground at the bottom of docs/onboarding/decoder.html and part 1 of docs/onboarding/assets/viz3d.js. Update them, then open the 3D view, press F12 and run Viz3D.selfTest(): it must answer ok: true.

…I want to change a constraint or the energy model

  1. Constraints are checked inside the inner loop of detail::greedyDecode; energy is deducted at commit.
  2. Satellite budgets come from create_satellites_from_csv; the energy rate from SimulationSnapshot.energyPerMinute.
  3. Read the energy quirk: every result depends on it.

…I want to change a genetic operator or a GP parameter

  1. Operators: tree_operators.h. Loop and selection: solveNextGeneration() in scheduler_gp.h.
  2. New parameter: add it to initialize() with a default that reproduces the old behaviour, then to py::arg in bindings.cpp, then to GAConfig, default_config(), argparse and _dest_to_key in main.py, and one row to SETTINGS in menu.py so the menu offers it (tests/test_menu.py fails until the two agree). The row's help text is what the menu shows the user: say what the setting does and what turning it up, down, on or off changes.
  3. All randomness must use the pair's mt19937, so seeded runs stay reproducible.
  4. Add a test to tests/test_paper_features.py and an ablation configuration to thesis/experiments/run_ablation.py.

…I want to make it faster

  1. Read PERFORMANCE.md: it lists what has already been done and how speed was measured.
  2. The hot path is ExprNode::eval inside greedyDecode. Measure before and after with a fixed seed, and check that the output is identical.

…I want to use different data

  1. Produce a CSV with the same columns as data/example.csv, then run world_splitter on it.
  2. Check the rescaling ranges in data_factory.py: they are fixed numbers, not read from the data.

…I cannot get the original data

  1. Generate realistic data: python3 -m data_processing.realistic_trace --download, then ./run realistic. Read Realistic data before you use a single number from it.
  2. To change what is generated (arrival rate, battery, ground position, the simulated scheduler), follow the table at the end of that page. Parameters live in data_processing/realistic_trace/scenario.py, each with its source: a new value needs a source too.
  3. Run python3 -m unittest tests.test_realistic_trace -v and update the validation table of that page with the figures the generator prints.

…a run gives strange results

  1. Re-run with --seed to make it reproducible.
  2. Use --inspect-snapshots to look at the world it trained on.
  3. Re-score the best tree with evaluate_single (raw objectives), not its fitness.
  4. Check Known quirks before assuming a bug.

…I want to change the 3D view

  1. Everything is in docs/onboarding/assets/viz3d.js. Part 1 (MODEL) decides where a task goes and must stay equal to detail::greedyDecode. Part 2 (SCENE) draws: the Earth, the orbits, the links, the moving tasks.
  2. The sizes of the made-up world are constants in that file: WORLD_PRESETS (battery and sunset ranges), newJob (task durations), N_PLANES and PER_PLANE (number of satellites).
  3. To offer another input in the formula box, add it to TERMS in assets/formula.js. The decoder playground gets it too.
  4. No build step: save and reload the page. Run Viz3D.selfTest() in the console after touching part 1, and update the table "What is real and what is simplified" if the picture shows something new.

…my change makes a page of this guide wrong

Fix the page in the same change, update its "last checked" line, and add a dated line to the changelog. To add a page, copy an existing one and add it to NAV in docs/onboarding/assets/site.js.
