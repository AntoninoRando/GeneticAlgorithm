# Genetic Algorithm to Solve Scheduling Problem

_More information specified in the [documentation](/docs/build/latex/schedulerlib.pdf)._



## The Problem

1. A `job` (or `Task`) is sent to an Access Point;
2. The access point **schedules** the job among possible SEO satellites.


### Task Fields

- id
- arrival time
- type
- ram
- disk
- image size
- execution time
- transfer time
- number of hops
- name of the execution server

### Satellite Fields

- orbital sunset
- is an access point?
- evelation angle
- neighbors
- latency
- bandwitdth
- completed tasks
- cpu busy until...
- network busy until...
- cpu capacity
- network capacity
- enery reserved
- list of rejectde tasks
- remainig energy
- list of tasks
- list of dead tasks

## Project Structure

- `build`: Contains the build file (generated by `CMake`).
- `docs`: Contains documentation files for the `schedulerlib` python library.
- `include`: Contains the header files (`.h`) that implement the logic of the `schedulerlib` library.
- `tests`: Lightweight deterministic tests (`python3 -m unittest discover -s tests -v`, from the project root, after building).
- `scripts`: Contains bash script to run some functionalities (e.g., build the project, run the project, run the project in debug mode, or make the documentation).
`runConfigurations`: Contains `.json` files with differen configurations of parameters for running the simulation. Each file defines a specific simulation parameters.


## Building and Running the Project

### Requirements

- python
- pybind11
- CMake
- numpy
- matplotlib

If you're running inside a docker container, ensure to have everything installed by running these commands:

```shell
sudo apt-get update
sudo apt-get install -y python3 cmake
sudo apt install python3-pybind11
```

### Default Build

1. Make a `build` directory and move inside it:

```shell
mkdir build && cd build
```

2. Build the python module and copy it on the project directory:

```shell
cmake .. -DPYTHON_EXECUTABLE=$(which python3)
cmake --build .
cp scheduler*.so ..
```

The `scheduler*.so` file is the module that can be used by Python.

### Debug Build

```
# Option 1
cd build && cmake -DCMAKE_BUILD_TYPE=Debug .. && make

# Option 2
cd scripts && ./build-debug.sh
```


### Run the Debugger

There are different options. 

1. **VS Code**: Use the `(debug) Launch main.py` "run and debug" configuration. This option will launch the script and it can be debugged via VS Code. Killing the "run and debug" process will also kill the python script.
2. **VS Code**: Run the `main.py` scrip (`python3 main.py`) and then use the `(debug) Attach to main.py`. The python script prints the PID of the process, so select the right process when asked to do so. This option will attach the debugger to the script, thus terminating the "run and debug" process will not kil the python script.

Options 1 and 2 allows to use VS Code UI to debug. Otherwise, it can be managed via the terminal using the GDB commands to add breakpoints, continue the execution and logging variables.

3. Run the python script in debug mode:
    ```
    gdb python3

    (gdb) set breakpoint pending on
    (gdb) run main.py
    ```

4. Attach the debugger.
    ```
    # Terminal 1
    python3 main.py

    # Terminal 2 (once you see the PID printed)
    gdb -p <PID>
    ```

### Run Configurations

You can launch `main.py` from a named JSON config in `runConfigurations/`:

```shell
./run default
```

The launcher resolves `runConfigurations/default.json` and expands its CLI arguments for `main.py`.
You can still append extra flags if needed:

```shell
./run default --generations 10
```

## Algorithm Parameters

- **Population**: number of scheduling algorithms to evolve each generation.
- **Generations**: number of training generations.
- **Max depth**: maximum depth of each individual.
- **Convergence treshold**: limit number of generations after which, if the fitness did not improve significantly, a new simulation is used.

## Metrics Instrumentation and Graphs

The main loop now records per-generation metrics and writes three artifacts:

- `<prefix>_metrics.csv`: append-only generation logs.
- `<prefix>_metrics.npz`: NumPy arrays for post-processing.
- `<prefix>_metrics.png`: graph built from NumPy data.

Run with metrics enabled (default):

```shell
python3 main.py --no-start-prompt --generations 200 --population 100 \
  --metrics-dir metrics --metrics-prefix run_01 --metrics-flush-every 1
```

Disable metrics when needed:

```shell
python3 main.py --disable-metrics
```

## Snapshot Inspection

You can inspect the full simulation snapshot (initial world, every world reset, and final evaluation snapshot) directly from `main.py`.

Print readable summaries:

```shell
python3 main.py --inspect-snapshots
```

Save snapshots to JSON:

```shell
python3 main.py --inspect-snapshots --save-snapshots \
  --snapshots-dir snapshots --snapshots-prefix run_01
```

Build a timeline graph from one snapshot (red dots: satellites, blue dots: tasks):

```shell
python3 snapshot_timeline_plot.py snapshots/<snapshot_file>.json
```

Specify output file:

```shell
python3 snapshot_timeline_plot.py snapshots/<snapshot_file>.json \
  --output snapshots/<snapshot_file>_timeline.png
```

## GP options taken from the literature

Every choice in `include/scheduler/*.h` carries a *LITERATURE NOTES* comment that
names the paper and section it comes from (bib keys of `thesis/references.bib`;
per-paper summaries in `thesis/literature_notes.md`). Seven refinements are
available as opt-in flags; **with none of them the algorithm is bit-for-bit the
previous one** (same seed, same output).

| Flag | What it does | Source |
|---|---|---|
| `--tournament-size K` | selection pressure (default 5) | Sun 2024 and Yang 2025 use 7, Zhang & Yang 2025 use 2 |
| `--initial-max-depth D` | initial trees shallower than the cap, so crossover can grow them | Sun, Yang, Zhang & Yang, Koza |
| `--internal-crossover-bias P` | prefer operator nodes as crossover points | Koza 1994, Sec. 4 (0.9) |
| `--clone-retries N` | re-mutate offspring identical to a parent or an elite | Zhang & Yang 2025, Sec. 3.2.1 (structural proxy of the repetition test) |
| `--terminal-weighting` | learn terminal probabilities for mutation by maximum likelihood (water filling) | Yang et al. 2025, Sec. IV-D |
| `--track-busy-until` | make `sat.cpuBusyUntil` a live "free at" terminal | Zhang & Yang 2025 (NT, CL), Sun 2024 (AAT, IAT) |
| `--prune-constant-terminals` | never draw terminals that are constant in the data | registry notes (4 of 17 terminals are always 0) |
| `--worlds-per-eval K` | score each individual on K worlds (pooled) | Yang 2025 (5 instances), Zhang & Yang 2025 (100 runs) |

`python3 main.py -c robust` turns on the two that helped (`clone_retries: 3`,
`worlds_per_eval: 3`).

### Measured effect

`thesis/experiments/run_ablation.py` trains each option on worlds 0-19 and scores
it on the 10 held-out worlds (same setup as the thesis experiments: population
100, depth 4, 300 generations), 20 paired seeds per configuration, then repeats
the promising ones on 20 fresh seeds. Test completion ratio, mean:

| | seeds 0-19 | seeds 100-119 |
|---|---|---|
| baseline | 0.223 | 0.227 |
| `--clone-retries 3` | 0.251 (p = 0.005) | 0.246 (p = 0.27) |
| `--worlds-per-eval 3` | 0.248 (p = 0.014) | 0.247 (p = 0.045) |
| tournament 7 / initial depth 3 / crossover bias / terminal weighting / pruning / busy-until | 0.221-0.235, none significant | - |

The gain is robustness more than a better optimum: the baseline ends on a
degenerate FCFS-like rule in 16 of 40 runs, against 0 of 40 with clone retries
and 1 of 40 with three worlds, and final population diversity rises from 0.57 to
0.97 / 0.86. Mean response time gets slightly worse (about +0.2 to +0.6 min).
The effects are modest, the first-set p-values are uncorrected for 10
comparisons, and the confirmation set is weaker; see the notes at the top of
`include/scheduler/scheduler_gp.h`. Raw results are in
`thesis/experiments/results_ablation/`.
